# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Status**: ACTIVE
**Last Updated**: July 11, 2026

## Overview

Apple Mail MCP server for Claude Code. Reads, searches, archives, deletes, marks, composes, and replies to email across all accounts. Non-Gmail accounts (iCloud, Exchange, IMAP) go through ScriptingBridge to Mail.app for every operation; Gmail-authorized accounts are Gmail-API-only (issue #50) for list, search, compose, reply, archive, delete, mark read/unread, and unread counts (issue #101) - flag and move stay ScriptingBridge-only for all accounts, including Gmail, as a deliberate exception (see MCP Tools table). No credentials required for Apple Mail access - macOS TCC handles it. Gmail OAuth tokens stored in `~/.config/mail-tools/`.

## Setup

```bash
# Install
pip install -e .

# Register MCP server (user scope)
claude mcp add -s user mail -- mail-mcp
```

On first run, macOS prompts for Automation access to Mail.app. Grant it once; TCC remembers the decision.

For the optional Gmail API integration (list/search/compose/reply/archive/delete/mark, see Two backends below):
```bash
# Authorize Gmail OAuth (opens browser)
mail-mcp  # then call gmail_authorize tool
```

## Architecture

```
mail_tools/
├── __init__.py
├── __main__.py
├── mail.py          # MailManager - ScriptingBridge to Mail.app
├── gmail.py         # GmailClient - OAuth2 via Gmail API
├── rules.py         # Sender-rules persistence (sender_rules.json) - load/save/query-build/staleness
├── search.py        # Deep search combining Mail.app + Gmail
└── mcp_server.py    # FastMCP server (JSON output)
```

**Two backends**: Mail.app via ScriptingBridge for standard operations and `mail_deep_search` (which reads Mail.app's local SQLite Envelope Index directly); the Gmail API is used for `mail_archive`/`mail_delete`/`mail_mark_read`/`mail_mark_unread` on Gmail-authorized accounts, all batched via `GmailClient.batch_modify()` (chunked `messages.batchModify`, <=1000 ids/call).

`mail_archive` was smoke-tested live (issue #46, 2026-07-01) and confirmed `batchModify` succeeds silently even when some messages in the batch already lack the label being removed. `mail_mark_read`/`mail_mark_unread`'s ScriptingBridge mailbox-scan fallback (the "Pass 4" step in `MailManager._mark_messages`, used when a message isn't found in an account's INBOX, an rfc822msgid: search, or a direct Gmail id lookup - see the Pass 3 paragraph below) is a non-Gmail-only path by hard invariant, not an incidental gap: a Gmail-authorized account whose message id resolves via none of Pass 1/2/3 is reported `not_found`, full stop - it is never handed to a ScriptingBridge mailbox scan, since that would reintroduce the per-account brute-force behavior issue #50 exists to remove.

`mail_archive`/`mail_delete`/`mail_mark_read`/`mail_mark_unread` gained a third resolution path (issue #89) for a Gmail-internal message id (the bare hex ids `mail_list`/`mail_search`/`mail_bulk_action` return for Gmail-authorized accounts) belonging to a message that has left INBOX entirely - already archived, or filtered straight to a category/label on arrival - and is therefore invisible to both Pass 1's per-account INBOX scan and Pass 2's `rfc822msgid:` search (that operator matches only actual RFC 5322 Message-IDs, never a bare Gmail-internal id). `MailManager._resolve_missing_gmail_ids()` (shared by all four tools) checks each Gmail-authorized account directly via `GmailClient.message_exists()` - a cheap `format=minimal` fetch that returns `False` (not an exception) on a 404, same contract as `get_message()` - to find which account owns a still-unresolved id; ids with an `"@"` are never attempted (same Gmail-internal-id heuristic `mail_read` uses, issue #87), so a genuinely-missing non-Gmail message costs zero extra API calls. Once ownership is confirmed, the actual mutation goes through `GmailClient.modify_by_gmail_id()` - a direct `batch_modify()` call, NOT `archive_messages()`/`delete_messages()`/`mark_read_messages()`/`mark_unread_messages()`, since those treat their input as an rfc822 Message-ID and would re-run the exact `rfc822msgid:` search that already failed to resolve the id in Pass 2. A dead/expired token on one authorized account during this lookup is logged and skipped via `_call_gmail_batch`, same as Pass 2, so it never aborts resolution for an id belonging to a different, healthy account.

`mail_read` (issue #87) resolves Gmail-internal message ids - the ids `mail_list`/`mail_search`/`mail_bulk_action` return for Gmail-authorized accounts, which are bare hex strings, not rfc822 Message-IDs - that ScriptingBridge's `messageId()`-based lookup can never match. `MailManager.read_message()` tries ScriptingBridge's fast unified-inbox check first (a single cheap IPC call); if that misses AND the id contains no `"@"` (RFC 5322's msg-id syntax always requires one, while Gmail's internal ids never have one), it tries `GmailClient.get_message()` against every Gmail-authorized account in turn - `mail_read` takes no `account` parameter, so which account owns a given id is unknown upfront - before falling back to ScriptingBridge's slow all-mailboxes scan. A dead token or any other per-account failure is logged and skipped via `_call_gmail_batch`, same as the Pass 2 fallback in `_mark_messages`/`archive_messages`/`delete_messages`. The `"@"` heuristic means the common non-Gmail case (every rfc822-style id) skips the Gmail branch entirely and goes straight to the slow scan exactly as before this issue - unaffected. `GmailClient.get_message()` fetches `format=full` (metadata + body) and returns `None` (not an exception) on a 404, since "this account doesn't have this id" is an expected outcome when trying several accounts in turn, not a genuine failure; `_extract_plain_text_body()` walks the MIME tree for a `text/plain` part, recursing into nested multiparts (e.g. `multipart/alternative` nested inside `multipart/mixed` alongside attachments) before falling back to `text/html`. It is a deliberate two-pass walk, not a single depth-first pass (code review fix, issue #87): pass 1 (`_find_plain_text_part()`) searches every nested multipart sibling for plain text with NO html fallback anywhere, and only when that comes up completely empty does pass 2 allow an html fallback. A single-pass walk that recursed into one sibling and accepted THAT sibling's own html fallback got this wrong for a real MIME shape - e.g. `multipart/mixed` containing a `multipart/related` (inline images, html only, no plain part) ordered before a `multipart/alternative` (has both plain and html): the first sibling's html result would win and the second sibling's real plain text would never even be inspected, since sibling order depends on the sending mail client, not on this code. HTML fallback content is returned as raw, unstripped markup - unlike ScriptingBridge's rendered plain-text equivalent for an HTML-only message - a known gap, not yet addressed. Content truncation (`MAX_CONTENT_LENGTH`) is applied uniformly by `MailManager._finalize_content()` regardless of which backend supplied the content.

`mail_compose`/`mail_reply` route Gmail-authorized accounts through `GmailClient.send_message`/`create_draft` (issue #50) instead of Mail.app's ScriptingBridge outgoing-message flow, using the existing `gmail.modify` OAuth grant - no new scope or re-authorization required. Smoke-tested live against mrlesmithjr@gmail.com (issue #50, 2026-07-02): a draft-only compose returned a `gmail_draft_id`; a send-to-self compose returned a `gmail_id` and delivered; a reply to that message returned its own `gmail_id`, and a direct API check confirmed the reply's `threadId` matches the original message's `threadId` - `resolve_thread()`'s `In-Reply-To`/`References`/`threadId` handling threads correctly, not just sends successfully. `from_account` omitted still uses Mail.app's default-identity ScriptingBridge path (documented exception - no way to query Mail.app's implicit default account before choosing a route); a `from_account` that doesn't resolve raises `MailError` rather than silently falling through.

`mail_list`/`mail_search` also route Gmail-authorized accounts through `GmailClient.list_messages`/`search_messages` (issue #50) for the unified inbox, single-account INBOX, and (for `mail_list` only) an explicit account's arbitrary mailbox; ScriptingBridge is now used only for non-Gmail (iCloud/other) accounts, plus `mail_list`'s no-account arbitrary-mailbox lookup and `mail_search`'s non-INBOX mailbox on a Gmail account (`GmailClient.search_messages` has no mailbox-scoping parameter, unlike `list_messages`, which accepts an `in:<mailbox>` query - a Gmail account searched outside INBOX still uses ScriptingBridge's substring match). Gmail and ScriptingBridge search semantics genuinely diverge, not just in transport: ScriptingBridge does a client-side, case-insensitive substring match of `query` against subject OR sender only, while a Gmail-routed `mail_search` sends `query` straight into Gmail's own full-text query engine (body content included, plus operators like `from:`/`has:attachment`/`newer_than:`) - the same query string can match nothing on one backend and plenty on the other. `GmailClient.list_messages` fetches a single page (`maxResults=<n>`, no pagination), unlike ScriptingBridge's always-full-mailbox fetch; `unread_only=True` pads that page request (up to 200) to reduce, not eliminate, the chance an older unread Gmail message falls outside the fetched page before the merged sort/filter/limit ever sees it.

`mail_unread` (issue #101) routes Gmail-authorized accounts through `GmailClient.get_unread_counts()` instead of ScriptingBridge's `mb.unreadCount()`, to avoid IMAP-sync lag as a general class of problem and the Mail.app-launch dependency entirely for a Gmail-authorized account. (An earlier version of this doc claimed a specific observed discrepancy between ScriptingBridge and the Gmail API for one mailbox - that claim was verified false and retracted; see `GmailClient.get_unread_counts()`'s own history for the correction.) `users.labels.list` (`GmailClient.list_labels()`) has no unread-count field, so `get_unread_counts()` issues one `users.labels.get` call per label to read its `messagesUnread`, returning one `{mailbox: label_name, unread}` entry per label with `messagesUnread > 0` - the same shape `MailManager.get_unread_count()`'s ScriptingBridge branch already produced, so the JSON returned to callers is unaffected by which backend produced it; a single label's GET failing is logged and only that label skipped, not the whole account's result. A dead/expired token (or any other per-account failure) is logged and skipped via `_call_gmail_batch`, same as archive/delete/mark, so one broken Gmail account reports zero unread rather than aborting results for other accounts. `GmailClient.is_authorized()` is case-insensitive, matching `_account_matches()`'s existing convention for account filters elsewhere in this package. Both of `get_unread_count()`'s Gmail-routing branches (an explicit email filter, and the no-filter per-account loop) key their result by the account's email address rather than `acct.name()`, since the email-filter fast path has no Mail.app display name available to it without the exact ScriptingBridge call it exists to avoid - this is the one Gmail-routed tool whose "account" field is an email address rather than a Mail.app display name. Non-Gmail accounts (e.g. iCloud) are unaffected and keep using `mb.unreadCount()`.

`mail_bulk_action` (issue #45) is a third, Gmail-API-only path: `GmailClient.search_ids()` queries Gmail's own index directly (native query syntax, paginated `messages.list`) to get Gmail-internal ids with no rfc822 Message-ID translation and no per-message Mail.app listing step at all - this is what makes "clean up everything from sender X" cheap even at 1000+ messages (one paginated list call + 1-2 `batchModify` calls vs. thousands of individual round-trips). `GmailClient.search_messages_preview()` backs the dry-run path: an exact `matched_count` from full `search_ids()` pagination, plus per-message metadata fetched only for a small (default 10) sample - never for the full matched set.

`mail_archive`/`mail_delete`/`mail_mark_read`/`mail_mark_unread` scan every Gmail-authorized account (Pass 1's per-account INBOX batch, Pass 2's rfc822msgid fallback, and Pass 3's direct-id lookup, all across `list_authorized_accounts()`) to resolve target ids regardless of which account they actually belong to. A dead/expired token on any one of those accounts used to raise and abort the whole call, even when the target ids belonged to a different, healthy account (issue #83). `MailManager._call_gmail_batch()` wraps every per-account Gmail API call in all three passes, logging a warning and skipping just that account on failure - the ids that account was resolving come back as a failed result (Pass 1) or fall through to the next authorized account (Pass 2/Pass 3), instead of the whole batch dying.

`mail_apply_rules` (issue #48) builds on `mail_bulk_action` rather than reimplementing it: sender-based categories are persisted in `~/.config/mail-tools/sender_rules.json` (same `CONFIG_DIR` convention as the Gmail credentials/tokens files), each with a `senders` list, a `default_action` (`archive`, `mark_read`, `archive_and_mark_read`, or the apply-rules-only `hold` meaning "never archive/mark-read"), a `status` (`active`, `paused`, `leave_alone`, `needs_review`), and an optional `apply_label` (issue #58). `MailManager.apply_rules()` filters to `status == "active"` BEFORE calling `bulk_action()` once per targeted category; a `default_action == "hold"` category is also filtered out UNLESS it carries `apply_label`, in which case it is deliberately targeted as a label-only category (hold means "no archive/mark-read", not "never touch"). This filter applies even to category ids explicitly requested via `category_ids`, so a held-back category (no `apply_label`) can never be mutated by naming it directly. `confirm=True` writes `last_reviewed` back to `sender_rules.json` only for categories actually executed. `rules.stale_categories()` is a separate, purely informational check (never a mutation trigger) surfaced as a `stale_reviews` block on every dry run.

Custom Gmail labels (issue #58) let a category stay visible in the inbox while still being tagged, instead of the only options being archive-and-hide (`archive`/`archive_and_mark_read`) or leave-completely-untouched (`hold` with no label). `GmailClient.list_labels()`/`create_label()`/`resolve_label_id()` back this: `create_label()` treats a 409 (label already exists) as success by re-listing and returning the existing label, so creating the same label twice never raises or duplicates it. `resolve_label_id()` delegates its lookup to `find_label()` (issue #85's refactor - same cache-check-then-list-refresh logic, minus the create-on-miss tail) and only calls `create_label()` on a `None` result; `find_label()` caches `email -> {name: id}` on the `GmailClient` instance (a process-lifetime singleton via `MailManager`/`_mail()`), so repeated `mail_bulk_action`/`mail_apply_rules` calls for the same label name within one session cost at most one label-list call and one label-create call total - true as long as the MCP SDK dispatches tool calls synchronously on one thread (it does today); the cache has no lock, so concurrent dispatch could race two cache misses into an extra list/create call, though `create_label()`'s 409 recovery still converges on the same id either way. `MailManager.bulk_action()` takes `apply_label`/`remove_label` parameters: when `apply_label` is set, it resolves the label id (creating it if needed) and passes it as `add_label_ids`; when `remove_label` is set, it resolves via `find_label()` only (NEVER creates - removing a label that was never applied is a legitimate no-op) and, if found, folds its id into `remove_label_ids` alongside the `action`'s own removals (empty for `action="hold"`, so a label-only request never touches INBOX/UNREAD) - one `batchModify` call does all of it, including the "swap" case of `apply_label` + `remove_label` together. `action="hold"` with neither `apply_label` nor `remove_label` raises, since that combination would be a fully no-op call. A `remove_label` naming a nonexistent label reports `remove_label_found: False` rather than raising.

The full label lifecycle (issue #85) is `mail_labels` (list), `mail_bulk_action`'s `apply_label`/`remove_label` (tag/untag matches), `mail_label_delete` (remove a label entirely), and `mail_label_rename` (rename in place). `GmailClient.find_label()` is the shared lookup all four of `resolve_label_id()`/`delete_label()`/`rename_label()`/`bulk_action()`'s `remove_label` path use - it never creates. `MailManager.delete_label()` is idempotent by design: a name that doesn't resolve returns `{"label": name, "found": False}` in either `confirm` state, never an error, and `confirm=False` always previews `messages_affected` (via `search_messages_preview('label:"<name>"')`, quoted so a multi-word name is matched as one term) without deleting. Deleting a label can never touch a message's INBOX/UNREAD/TRASH state, structurally - `GmailClient.delete_label()` only ever issues a `DELETE users/me/labels/{id}` call, incapable of a `batchModify`. `MailManager.rename_label()` is NOT tolerant of a missing name the way `delete_label()` is - `old_name` names a single specific target, so a typo raises `MailError` immediately rather than silently no-opping. `GmailClient.rename_label()` PATCHes the same label id with a new `name`, so every message that carried the label keeps it under the new name with no `batchModify` call needed; the cache pops `old_name` and adds `new_name -> id`, so a subsequent lookup by the old name (now genuinely gone) correctly creates a brand new label rather than resurrecting the renamed one.

### Prompt Injection Guarding (issue #115)

`mail_read`/`mail_search`/`mail_deep_search` return raw email content (subject, sender, body) into the model's context in the same conversation as this server's write-capable tools (`mail_compose`, `mail_reply`, `mail_move`, `mail_delete`, `mail_bulk_action`, `mail_apply_rules`), making an attacker-controlled email an indirect-prompt-injection vector. `mcp_server.py` uses the `prompt-security-utils` PyPI library (MIT, `andmarios/prompt-security-utils`) to guard against this: `generate_markers()` runs once at module load to produce a session-unique `(_MARKER_START, _MARKER_END)` pair, `security_instructions()` folds those markers into the `FastMCP(instructions=...)` string (the trusted channel the model reads before any email content), and `_wrap_untrusted_field()` (a thin wrapper over the library's `wrap_field()`) wraps `subject`/`from`/`content` in `mail_read`, `subject`/`from` per result in `mail_search`, and `subject`/`sender_name` per result in `mail_deep_search` (which has no `message_id` or `content` field - see `search.py`'s `deep_search()` shape - so it uses a `deep_search:<index>` source id instead, and leaves `sender_email` unwrapped since it isn't free-text authored content). `wrap_field()` returns `None` unchanged for a `None` input (e.g. a missing `from` header), so an absent field stays absent rather than becoming a wrapped-`None` object. The module constructs its own `SecurityConfig(semantic_enabled=False, llm_screen_enabled=False)` rather than calling the library's `load_config()` (which reads a shared `~/.config/prompt-security-utils/config.json` other tools could also write to) - this keeps mail-tools' wrapping behavior deterministic and scoped to marker wrapping plus the library's built-in regex `detection_enabled` tier; the semantic tier is deliberately left off since enabling it would trigger a fastembed transformer model download into the mail-tools hot path, out of scope for this issue. `semantic_enabled=False` only avoids that runtime model download, though - it does NOT avoid the install-size cost: `prompt-security-utils==1.4.0` pulls in `fastembed` (and its `onnxruntime` dependency, ~68MB installed) as a hard, unconditional dependency with no optional-extras mechanism, so mail-tools pays that install weight on every SessionStart venv rebuild regardless of this flag.

A code-review pass on the initial fix (issue #115, 2026-07-11) found it real but incomplete: `mail_list` and `mail_bulk_action`'s dry-run `sample` were still returning raw, unwrapped `subject`/`from` - `mail_list` matters most since it's the first tool most conversations call, reaching the model before `mail_read`/`mail_search` are ever invoked. Both now use the same `_wrap_untrusted_field()` pattern, with `message_id` (falling back to `mailbox` for `mail_list` or `query` for `mail_bulk_action`) as the source id.

A second code-review pass (issue #115, 2026-07-11) found the same gap one level deeper: `mail_apply_rules` calls `MailManager.apply_rules()`, which calls `MailManager.bulk_action()` directly - the manager method, NOT the `mail_bulk_action` tool wrapper fixed above - and spreads its raw dry-run `sample` straight into each category's result dict. Since `confirm=False` is `mail_apply_rules`' default, a typical dry-run call surfaced raw attacker-controlled `sample[].subject`/`from` per category. The fix wraps each category's `sample` at the `mcp_server.py` tool boundary (same as the other four call sites), not in `mail.py`. This same review also flagged the wrap-a-message-list loop as duplicated four times over (`mail_list`, `mail_search`, `mail_deep_search`, `mail_bulk_action`); `_wrap_message_list()` in `mcp_server.py` is the shared helper all five wrap-sites (including `mail_apply_rules`' per-category sample) now call, parameterized by `fields` (`("subject", "sender_name")` for `mail_deep_search`, `("subject", "from")` elsewhere) and by `fallback_id` (a plain string, or - `mail_deep_search` only, since its dicts carry no `message_id` at all - a callable taking the index and returning `f"deep_search:{idx}"`).

A third code-review pass (issue #115, 2026-07-11) found `mail_reply` echoing the original message's raw, attacker-controlled `subject` straight back in its response - the reply tool reads the source message to build its own reply, so that subject is just as untrusted as anything `mail_read`/`mail_search` return. The fix wraps it with `_wrap_untrusted_field()` at the `mcp_server.py` tool boundary, using `message_id` as the source id, same convention as every other wrap site. A full sweep of every remaining `@mcp.tool` in the file found no further gaps; this closes issue #115.

## MCP Tools

| Tool | Description |
|------|-------------|
| `mail_accounts` | All configured mail accounts |
| `mail_mailboxes(account?)` | Mailboxes with unread/total counts |
| `mail_unread(account?)` | Unread message counts per account - Gmail-authorized accounts route through the Gmail API (issue #101, live per-label `messagesUnread` via `users.labels.get`) instead of ScriptingBridge's `mb.unreadCount()`, which reads Mail.app's locally IMAP-synced state and can lag behind Gmail's actual server-side unread count; non-Gmail accounts (e.g. iCloud) are unaffected |
| `mail_list(mailbox?, account?, limit?, unread_only?)` | List messages - non-Gmail accounts always batch-serialize the full target mailbox before sorting/filtering/limiting; Gmail-authorized accounts route through the Gmail API (INBOX cases, and an explicit account's arbitrary mailbox), which fetches only a single page (padded when `unread_only=true`). Each result's `subject`/`from` are wrapped with session security markers (issue #115) |
| `mail_read(message_id)` | Read a message body - automatically resolves Gmail-internal ids (issue #87): an id with no "@" tries every Gmail-authorized account via the API before falling back to ScriptingBridge's slower all-mailboxes scan; an rfc822-style id (has "@") goes straight to ScriptingBridge, unaffected. `subject`/`from`/`content` are wrapped with session security markers before being returned (issue #115, see Prompt Injection Guarding below) |
| `mail_search(query, mailbox?, account?)` | Substring match on subject/sender via Mail.app for non-Gmail accounts and non-INBOX mailboxes; for Gmail-authorized accounts searched with mailbox=INBOX (default), `query` is Gmail's own full-text search instead - not the same search semantics, see CLAUDE.md. Each result's `subject`/`from` are wrapped with session security markers (issue #115) |
| `mail_deep_search(query, max_results?)` | Full-text search via Mail.app's local SQLite Envelope Index. Each result's `subject`/`sender_name` are wrapped with session security markers (issue #115); `sender_email` is left unwrapped |
| `mail_compose(to, subject, body, cc?, bcc?, account?)` | Compose and send |
| `mail_reply(message_id, body, reply_all?)` | Reply to a message. `subject` in the response is wrapped with session security markers (issue #115) |
| `mail_mark_read(message_ids)` | Mark one or more messages as read (comma-separated; Gmail-authorized accounts are Gmail-API-only end to end - never fall back to a ScriptingBridge mailbox scan, even when unresolved by the API. Resolves a Gmail-internal id for a message no longer in INBOX via a direct per-account lookup (issue #89) before giving up. Non-Gmail accounts get a ScriptingBridge mailbox-scan fallback for messages already filed elsewhere) |
| `mail_mark_unread(message_ids)` | Mark one or more messages as unread (same batching/fallback as `mail_mark_read`) |
| `mail_flag(message_ids, flagged?)` | Flag or unflag one or more messages (comma-separated; ScriptingBridge-only for every account including Gmail - deliberate exception to the #50 Gmail-API-only migration, since Gmail's STARRED-label equivalent needs label support; `mail_bulk_action`/`mail_apply_rules` now support arbitrary custom labels (issue #58), but `mail_flag` itself still targets only the built-in STARRED flag and remains ScriptingBridge-only) |
| `mail_archive(message_ids)` | Archive one or more messages (comma-separated; Gmail accounts via the API remove the INBOX label; others fall back to mark-as-read. Resolves a Gmail-internal id for a message no longer in INBOX - e.g. already archived, or filtered straight to a category/label on arrival - via a direct per-account lookup (issue #89) before reporting not found) |
| `mail_move(message_id, mailbox)` | Move to a mailbox (ScriptingBridge-only for every account including Gmail - deliberate exception to the #50 Gmail-API-only migration, since Gmail has no folder-move equivalent; for a Gmail account prefer `mail_archive`/`mail_delete`, or `mail_bulk_action`/`mail_apply_rules` with `apply_label` (issue #58) to tag a message with a custom label instead of moving it) |
| `mail_delete(message_ids)` | Delete one or more messages (comma-separated; known issue - prefer mail_move to Trash. Same Gmail-internal-id direct-lookup fallback as `mail_archive` (issue #89)) |
| `mail_bulk_action(account, query, action, confirm?, apply_label?, remove_label?)` | Bulk archive/mark-read/label Gmail messages matching a native Gmail search query (Gmail-API-only, no ScriptingBridge fallback). Defaults to a dry run (`confirm=false`) returning `matched_count` + a sample of up to 10 matches, each with `subject`/`from` wrapped with session security markers (issue #115), plus `apply_label`/`remove_label` echoed back when set; `confirm=true` re-runs the search fresh and executes via chunked `batchModify` (this response has no `sample` field, so nothing to wrap). `action` is one of `archive`, `mark_read`, `archive_and_mark_read`, `hold` (no archive/read mutation) - no delete action. `apply_label` (issue #58) applies a custom Gmail label to every match, creating it first if it doesn't already exist (idempotent); the response then also carries `label_created` (true only if this call created the label). `remove_label` (issue #85) removes a custom Gmail label from every match in the same `batchModify` call, never creating it - naming a label that doesn't exist is a safe no-op reported via `remove_label_found: False`, not an error. Combine `apply_label` and `remove_label` together to swap matches from one label to another in one call, or combine either with `action="hold"` to tag/untag matches without archiving or marking read. `action="hold"` with neither `apply_label` nor `remove_label` raises, since it would be a fully no-op call |
| `mail_apply_rules(account, category_ids?, confirm?)` | Apply persisted sender-rule categories (`~/.config/mail-tools/sender_rules.json`) to an account, calling `mail_bulk_action`'s logic once per targeted `status=="active"` category (default: all active categories, or an explicit comma-separated `category_ids` subset). Categories with `status != "active"` are always skipped before any mutation, even if named explicitly in `category_ids`; a `default_action == "hold"` category is also skipped UNLESS it carries an `apply_label` (issue #58), in which case it is deliberately targeted as a label-only category. Dry run (`confirm=false`, default) returns per-category `matched_count` plus a `sample` of up to 10 matches (each with `subject`/`from` wrapped with session security markers, issue #115) and a `stale_reviews` nudge (any category whose `review_after_days` has elapsed, regardless of status); `confirm=true` executes and writes `last_reviewed` back only for categories actually run |
| `mail_labels(account)` | List every label (system + custom) for a Gmail-authorized account - `{id, name, type}` per label (issue #85) |
| `mail_label_delete(account, name, confirm?)` | Delete a custom Gmail label by name (issue #85). Idempotent: a name that doesn't resolve returns `{"label": name, "found": False}` in either `confirm` state, never an error. `confirm=false` (default) previews `messages_affected` without deleting; `confirm=true` deletes after computing that same count. Can never change a message's INBOX/UNREAD/TRASH state, structurally - only ever issues a `DELETE users/me/labels/{id}` call |
| `mail_label_rename(account, old_name, new_name)` | Rename a custom Gmail label in place, preserving its Gmail-internal id (issue #85) - every message that carried it keeps it under the new name, via a single `PATCH`, no `batchModify` needed. Unlike `mail_label_delete`, a not-found `old_name` raises rather than silently no-opping, since it names one specific target |
| `gmail_authorize` | Start Gmail OAuth flow |
| `gmail_status(verify?)` | Check Gmail OAuth token status. `verify=true` (default) makes one `users.getProfile` call per authorized account to confirm the token actually still works, since a token-file entry alone doesn't mean the refresh token hasn't been revoked/expired; returns `live: true/false/null` per account (`null` when `verify=false`, or when the live check itself failed for a reason unrelated to the token, e.g. a network outage - see that account's `error`). `verify=false` skips the network calls entirely (offline, no API quota) |

## Key Patterns

- Prefer batch operations - rapid sequential ScriptingBridge calls can spike Mail.app CPU
- Collecting "which messages match these ids" from a mailbox uses `arrayByApplyingSelector_("messageId")` (one IPC call) instead of a per-message `.messageId()` loop - see `_match_messages_by_id()` in `mail.py`
- Use `mail_move` to Trash instead of `mail_delete` - delete has a known issue
- Gmail OAuth tokens cached at `~/.config/mail-tools/gmail_tokens.json` (600 permissions)
- Gmail bulk label changes go through `GmailClient.batch_modify()`, chunked to <=1000 ids per `messages.batchModify` call. A 429/quota-403 chunk failure backs off and retries the whole chunk (up to `RATE_LIMIT_MAX_RETRIES`, then raises); any other chunk failure (e.g. one bad id) falls back to a per-message retry
- All tools return structured JSON; errors return `{"error": "..."}`
